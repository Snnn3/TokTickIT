# Lab 2 Sprint Engineering Specification - TokTickIT Requester MVP

Status: Approved contract draft for Issue #16 | Version: 1.0 | Date: 2026-08-24
Companion documents: `api-spec.md`, `ui-spec.md`, `tests.md` (same folder).

## 1. Sprint Goal

Deliver the Requester-facing TokTickIT MVP: a Development Requester selection screen (test-only
identity), Create Ticket with permitted attachments, My Tickets with search/filter/sort/pagination,
and a read-only Ticket Detail with an attachment lifecycle (add / download / soft-remove) - all
protected by backend ownership checks and presented in the reusable Zen Green design system.

## 2. Stakeholder Request Interpretation

The IT department needs real support requests from end users (Requesters). A Requester describes a
problem, classifies it (category, related system, requested priority), optionally attaches evidence,
and submits. The system issues the official Ticket Number, stores data safely, and guarantees one
Requester never sees another's tickets. Until real login arrives in Lab 3, a temporary Development
Requester Selection screen stands in for authentication purely for testing. All screens establish
the reusable Zen Green conventions later labs must reuse. The stakeholder gave product intent, not
an engineering spec; this document supplies the missing precision.

## 3. Scope

### Included

- Development Requester Selection screen and session context (selection, display, switching)
- Reference data loading (active Categories, active Related Systems)
- Create Ticket (validated form, optional attachments, backend-generated Ticket Number)
- My Tickets (owned tickets only; search, filters, sorting, pagination; responsive table/cards)
- Requester Ticket Detail (read-only ticket info)
- Attachment lifecycle on an existing ticket: add, download, metadata, soft-remove with reason
- Ownership enforcement on every ticket/attachment API operation
- Loading / empty / no-results / failure states on all screens
- Zen Green tokens, component rules, responsive layout, accessibility baseline
- Idempotent seed data; Prisma schema increment; REST API per `api-spec.md`
- Automated tests per `tests.md` (unit, API, UI component/style, responsive, E2E)

### Excluded

- Authentication/security of any kind (login, logout, passwords, hashing, sessions, tokens, roles).
  The Development Requester selector is a test mechanism, NOT authentication.
- IT Staff workflow (staff dashboard/queue, claim/reassign, IT Priority changes)
- Public Comments, Internal Notes, Actions Taken
- Any status transition beyond the initial New status (resolve/close/reopen/cancel)
- Administration (users, roles, reference-data management)

## 4. Functional Requirements

- **FR-01** The app loads active Development Requesters and offers a Selection screen before any
  requester-scoped screen is usable.
- **FR-02** Selecting a requester and pressing Continue establishes the session context, displays
  the requester's name in the app shell, and enables navigation.
- **FR-03** A Change Requester action clears context-bound data and returns to Selection; switching
  reloads all requester-specific data.
- **FR-04** Create Ticket loads active Categories and Related Systems from the API.
- **FR-05** Create Ticket accepts Summary, Description, Category, Related System, Requested
  Priority, and zero-to-five attachments, and submits them to `POST /api/tickets`.
- **FR-06** Both frontend and backend validate every rule; frontend shows instant field-level
  messages; backend rejects with structured errors (authoritative).
- **FR-07** On successful creation the UI shows the official Ticket Number generated by the backend
  plus a next action to view the ticket.
- **FR-08** My Tickets lists only the selected requester's tickets with debounced free-text search,
  filters (Category, Priority, Status), sorting, pagination controls, and result-count feedback.
- **FR-09** Ticket Detail presents all ticket fields read-only, visually distinct from editable areas.
- **FR-10** Ticket Detail allows adding permitted attachments subject to the same constraints as creation.
- **FR-11** Ticket Detail allows downloading any active attachment; removed ones cannot be downloaded or previewed.
- **FR-12** Ticket Detail allows soft-removing an attachment after a mandatory reason and confirmation.
- **FR-13** Every ticket/attachment API operation enforces that the requester identified by
  `X-Requester-Id` owns the resource.
- **FR-14** The app shell shows TokTickIT identity, My Tickets and Create Ticket navigation with a
  clear active-page indication, the selected requester identity, and responsive mobile navigation.
- **FR-15** Every screen implements initial, loading, validation-error, submitting/busy, success,
  API-failure, empty-list, and no-results states as applicable (see `ui-spec.md`).

## 5. Business Rules

- **BR-01** The official Ticket Number is generated by the backend inside the creation transaction,
  formatted `TKT-{year}-{sequence}` (e.g., `TKT-2026-00001`); sequence is a monotonic Postgres
  sequence; numbers are unique forever even across year boundaries.
- **BR-02** Every new Ticket starts with Current Status `New`; no other status exists in Lab 2.
- **BR-03** The Development Requester selector is a testing mechanism standing in for login; it
  provides no security and must be labeled as such in the UI.
- **BR-04** The selector lists only active Requesters ordered by name ascending; inactive Requesters
  never appear anywhere selectable.
- **BR-05** The selection persists for the browser session (survives reload within the tab);
  switching selection discards loaded requester-scoped data before reloading.
- **BR-06** Each Ticket belongs to exactly one Requester; all list/detail/attachment operations are
  scoped to the requesting identity; cross-requester access returns HTTP 403.
- **BR-07** Ticket Summary is required; leading/trailing whitespace is trimmed; 1-150 characters after trim.
- **BR-08** Description is required; trimmed; 1-5000 characters after trim.
- **BR-09** Category is required and must reference an active Category.
- **BR-10** Related System is required and must reference an active Related System.
- **BR-11** Requested Priority is required; one of `LOW`, `MEDIUM`, `HIGH`. No implicit default is applied.
- **BR-12** Ticket Date is system-generated at creation (UTC) and read-only thereafter.
- **BR-13** Attachments are optional. Allowed types: JPG/JPEG (`image/jpeg`), PNG (`image/png`),
  WEBP (`image/webp`), PDF (`application/pdf`). Maximum size 5 MB per file. Maximum 5 active
  attachments per Ticket (creation-time and lifetime total combined).
- **BR-14** At creation, attachments are validated atomically: any invalid file rejects the whole
  submission (nothing is saved) with a precise per-file reason.
- **BR-15** If an attachment upload fails on an existing ticket (detail screen), the ticket itself
  remains untouched; a safe error is shown and the user may retry.
- **BR-16** Removal is always soft: `removedAt` timestamp and `removedReason` are recorded;
  attachment bytes and metadata remain stored; removed items stay visible as metadata but disabled.
- **BR-17** Soft removal requires a non-empty trimmed reason (max 300 characters) and explicit
  confirmation; only the owning requester may remove.
- **BR-18** Duplicate-submission prevention: while a create/add/remove request is in flight the
  triggering control is busy-disabled; further submits are impossible from the UI.
- **BR-19** Search performs case-insensitive substring matching on Ticket Number OR Summary only.
- **BR-20** Filters: Category (exact id), Priority (enum), Status (only `New`). Sortable fields:
  `updatedAt`, `createdAt`, `number`; default sort `updatedAt` descending with `number` descending tiebreak.
- **BR-21** Pagination: `page` starts at 1; `pageSize` in {5,10,20}, default 10; response carries
  `{page,pageSize,total,totalPages}`; invalid parameter values yield HTTP 400.
- **BR-22** Requests without a valid active `X-Requester-Id` are rejected HTTP 401 (test-mechanism
  equivalent of unauthenticated).
- **BR-23** On API failure during Create Ticket, all entered form values are preserved and a safe,
  generic error banner appears (no stack traces, no internal details).
- **BR-24** My Tickets distinguishes the empty state (requester has zero tickets) from the
  no-results state (filters/search matched nothing).
- **BR-25** Schema evolution: models keep stable surrogate-key relationships so Lab 3 can introduce
  real authentication without changing Ticket/Attachment ownership semantics.

## 7. Data Changes

PostgreSQL via Prisma. Conceptual models:

| Model | Key fields |
|---|---|
| RequesterUser | id (PK), name, email (unique), isActive, createdAt, updatedAt |
| Category *(existing)* | id (PK), name (unique), isActive, timestamps |
| RelatedSystem | id (PK), name (unique, <=120), isActive, timestamps |
| Ticket | id (PK), number varchar(20) unique, requesterId FK->RequesterUser, categoryId FK->Category, systemId FK->RelatedSystem, summary varchar(i), description text, requestedPriority enum, status enum(`NEW`), ticketDate timestamptz, createdAt, updatedAt |
| Attachment | id (PK), ticketId FK->Ticket (cascade), filename varchar(255), mimeType varchar(100), sizeBytes int, data bytea, uploadedAt, removedAt?, removedReason? varchar(300) |

Relationships (labsheet 5.1): one Requester -> many Tickets; one Ticket -> one Requester;
one Ticket -> many Attachments; one Category -> many Tickets; one RelatedSystem -> many Tickets.

Indexes/constraints: unique on `Ticket.number`, `RequesterUser.email`, reference names;
composite index `Ticket(requesterId, updatedAt)` serving the owned-list default query path;
index `Attachment(ticketId)` (FK) and partial-style check via `removedAt` nullability for active counts.
Enums: `TicketPriority {LOW, MEDIUM, HIGH}`, `TicketStatus {NEW}`.

Justified decision (labsheet 5.2 requirement): attachment bytes are stored in Postgres as `bytea`
rather than the filesystem. Rationale: at the 5 MB cap, DB storage makes ticket+attachments creation
a single transaction (BR-14 atomicity trivially correct), removal semantics need no filesystem
cleanup compensation, backups include evidence automatically, and grading/demo environments need no
volume mounts. Trade-off accepted: larger DB growth; mitigated by the 5-active-per-ticket cap.

Seed (idempotent, safe to rerun): 4 Categories (Account and Access, Hardware, Software, Network);
7 Related Systems (Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App, Printer, Corporate
Laptop); 4 active Requesters (Anucha Wongchai, Busaba Srisawat, Chatchai Promma, Duangjai Niran -
realistic example.com addresses); 1 inactive Requester (Noppadol Kaeo) who must never appear in the
selector. Upserts keyed on natural unique keys.

## 8. API Contract

Summary - full shapes in `api-spec.md`:

```
GET    /api/requesters                       active requesters for the selector
GET    /api/reference/categories             active categories
GET    /api/reference/systems                active related systems
POST   /api/tickets                          multipart create; atomic attachments; 201 + official number
GET    /api/tickets                          owned list: ?search&categoryId&priority&status&sort&order&page&pageSize
GET    /api/tickets/:id                      owned detail incl. attachment metadata
POST   /api/tickets/:id/attachments          multipart add (limits enforced)
GET    /api/attachments/:id                  owned attachment metadata
GET    /api/attachments/:id/download         stream bytes; 410 once removed
DELETE /api/attachments/:id                  soft remove {reason}; repeat -> 409
```

All requester-scoped endpoints require `X-Requester-Id` (BR-22 -> 401). Identity is a Lab 2 test
mechanism only. Error envelope: `{ "error": { "code", "message", "details"? } }`.

## 9. Acceptance Criteria

Format: Given / When / Then. Every AC maps to >=1 planned test in `tests.md`.

- **AC-01** Given valid ticket data, when the Requester submits the form, then exactly one Ticket is
  saved and its official Ticket Number is displayed from the backend response.
- **AC-02** Given no Development Requester is selected, when the user attempts to open My Tickets or
  Create Ticket, then the Requester Selection screen is shown instead.
- **AC-03** Given Requester B is selected, when a Ticket belonging to Requester A is requested
  (list, detail, or attachment operation), then the data is not returned (HTTP 403).
- **AC-04** Given the form lacks a Summary, when submitting, then a field-level message appears and
  no API call is made.
- **AC-05** Given Summary >150 or Description >5000 characters, when submitting, then per-field
  limit messages appear (client) and the backend rejects with 400.
- **AC-06** Given missing Category, Related System, or Priority, when submitting, then the specific
  field messages appear and the API is not called until fixed.
- **AC-07** Given a file of an unsupported type, when attached, then it is rejected with a clear
  message naming allowed types (client pre-check and backend 415 agree).
- **AC-08** Given a file larger than 5 MB, when attached, then it is rejected with a size message
  (client pre-check and backend 413 agree).
- **AC-09** Given a ticket already has 5 active attachments, when adding another, then the request
  is refused with a limit explanation (backend 409; UI disables the control).
- **AC-10** Given attachment processing fails during creation, when the transaction rolls back, then
  no ticket and no attachments persist and the user sees a safe error retaining form input.
- **AC-11** Given a removed attachment, when viewing Ticket Detail, then its metadata remains
  visible but download/preview actions are unavailable.
- **AC-12** Given the Remove action, when the reason is empty or confirmation declined, then
  nothing changes; given a valid reason confirmed, then the attachment becomes removed (soft) with
  `removedAt` and the recorded reason.
- **AC-13** Given a search term, when applied, then results contain the term in Ticket Number or
  Summary case-insensitively; non-matches are excluded.
- **AC-14** Given a Category or Priority filter, when applied, then only matching tickets are listed.
- **AC-15** Given a sort choice, when applied, then ordering follows it; absent choice defaults to
  Last Updated descending.
- **AC-16** Given pagination inputs including invalid ones, when requested, then valid requests
  return the correct slice plus `{page,pageSize,total,totalPages}` and invalid values produce a 400
  handled as a safe UI error.
- **AC-17** Given a requester with no tickets versus filters matching nothing, then the empty state
  and the no-results state render distinctly.
- **AC-18** Given Requester A's session, when switching to Requester B, then A's tickets disappear
  from every screen and B's own data loads.
- **AC-19** Given seeded active and inactive requesters, when the selector loads, then only active
  requesters are offered, ordered by name.
- **AC-20** Given the backend down or erroring during Create Ticket, when submission fails, then a
  generic error banner shows and all entered values remain in the form.
- **AC-21** Given a submission already in flight, when the user attempts to submit again, then the
  control is busy-disabled making duplicate submission impossible.
- **AC-22** Given desktop, tablet, and mobile viewports, when any screen renders, then layouts match
  the responsive table in `ui-spec.md` with no horizontal page scroll on mobile.
- **AC-23** Given Ticket Detail, when rendered, then ticket information is read-only and visually
  distinct from attachment action areas.
- **AC-24** Given keyboard-only interaction, when using the selector and forms, then all controls are
  reachable and focus indicators remain visible.

## 11. Assumptions and Decisions

| # | Decision / Assumption | Justification |
|---|---|---|
| A1 | Ticket Number `TKT-{year}-{5-digit seq}` from a single global sequence | Human-readable, sortable, collision-free across year rollover since the embedded sequence never resets |
| A2 | Priority enum LOW/MEDIUM/HIGH | Stakeholder examples show MEDIUM; three levels keep the badge system simple; extendable later |
| A3 | Summary max 150, Description max 5000 (chars, post-trim) | Summary must scan as one line in list views; Description allows detailed reproduction steps; both enforced FE+BE |
| A4 | Creation-time attachments are all-or-nothing | Matches bytea storage (one transaction); avoids orphaned tickets with partial evidence |
| A5 | Duplicate prevention via busy-disabled controls only | Adequate for single-user MVP; true idempotency keys deferred to Lab 3 auth work |
| A6 | `X-Requester-Id` header carries identity; unknown/inactive -> 401 | Cleanest swap point for real auth middleware in Lab 3 (BR-25) |
| A7 | pageSize whitelist {5,10,20}, default 10 | Prevents abuse-sized pages; predictable UI dropdown |
| A8 | Search limited to Number+Summary | Labsheet scope; full-text deferred |
| A9 | Client test folder normalized `client/src/**/__tests__/lab-02/` | Labsheet path contains a stray space; documented normalization |
| A10 | Timestamps UTC in DB, ISO-8601 in API | Unambiguous ordering; local rendering is a client concern |
